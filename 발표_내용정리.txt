재난문자 긴급도 자동 분류 시스템 — 발표 내용 정리
================================================================================

■ 프로젝트 개요
-------------------------------------------------------------------------------
과제명  : 한국 재난문자(CBS) 5단계 긴급도 자동 분류
목표    : 재난문자를 L0(긴급아님) ~ L4(매우높음) 5단계로 딥러닝 분류
데이터  : 공공데이터포털 재난문자 + 수동 레이블링 → dedup_v7 (136,987건)
모델    : KoELECTRA v3 기반 5-class classifier (v22, 완성)

최종 목표 (전부 달성):
  - MacroF1 ≥ 98%  →  달성: 98.75%
  - L4 Precision ≥ 95%  →  달성: 96.9%
  - Accuracy ≥ 98%  →  달성: 99.27%


■ 1. 레이블 정의
-------------------------------------------------------------------------------
레이블  이름        정의
L0      긴급아님    행동 불필요 (해제, 종료, 예방 안내, 훈련)
L1      낮음        주의 권고 (예보 수준, 잠재적 위험)
L2      중간        행정 조치 / 방역 협조 (상황 발생, 시설 대응)
L3      높음        야외 자제 / 예방적 조치 (재난 진행 중)
L4      매우높음    즉각 대피 명령 (생명 위협, 지금 당장)

핵심 원칙:
  "경보" 있어도 해제 공지이면 L0
  "대피" 없어도 즉각 위험이면 L4
  → 레이블은 특정 키워드 유무가 아닌 상황 심각성 + 행동 즉시성으로 결정


■ 2. 데이터셋 구성 (dedup_v7)
-------------------------------------------------------------------------------
항목            건수        비율
Train           95,890      70%
Validation      20,548      15%
Test            20,549      15%
합계            136,987     100%

주요 처리:
1) COVID 편향 제거
   - 2021년 이후 L0 COVID 문자 70% 제거
   - 이유: 모델이 "COVID = L0" 으로 암기 → 신종 감염병 분류 오류 방지
2) 합성 데이터 추가 (총 100건 → upsample 5배 → 305건)
   - COVID 키워드 없는 합성 L1 50건 + L2 50건
   - 이유: OOD 신종 감염병 케이스 일반화


■ 3. 모델 아키텍처
-------------------------------------------------------------------------------
베이스 모델: monologg/koelectra-base-v3-discriminator (KoELECTRA v3, ~110M params)
출력: 5-class softmax classifier

[핵심 기법 3가지]

① 키워드 마스킹 증강
  - 학습 시 긴급도 관련 키워드 25개를 ' '(공백)으로 치환
  - "즉시 대피", "경보", "주의보", "대피명령" 등
  - 목적: 키워드 없이도 문맥만으로 분류할 수 있도록 강제
  - 검증 방법: 마스킹 F1 (키워드 제거 후 평가)

② 3-Component 손실 함수
  L_total = CE(원본) + α_masked × CE(마스킹) + α_kl × KL(p_원본 ∥ p_마스킹)
  - CE(원본): 원본 텍스트 FocalLoss (γ=2.0)
  - CE(마스킹): 마스킹 텍스트 FocalLoss → 키워드 없는 맥락 학습
  - KL Divergence: 원본-마스킹 예측 분포 일치 → 일관성 강제

③ 학습률(LR) 스케줄 최적화 (v22 핵심 기법)
  - 문제: v21에서 L3↔L4 경계 혼란 → L4 Precision 89.9%
  - 변경: lr 2e-5 → 5e-5, warmup 10% → 20%, epochs 5 → 7
  - 효과: 손실 함수 구조 변경 없이 학습 스케줄 조정만으로
          L3↔L4 경계 혼란 완화 (L4 Precision 89.9% → 96.9%)


■ 4. 개발 과정 요약
-------------------------------------------------------------------------------
단계 1 : 3-class 분류 (긴급/주의/일반) → MacroF1 96.58%
단계 2 : 5-class 전환 — KLUE-BERT → MacroF1 99.43%, 마스킹 97.36%
단계 3 : KoELECTRA 전환, FocalLoss, WeightedSampler → 마스킹 97.3%
단계 4 : 3-component 손실 도입 → 토크나이저 오류로 무효 (v9~v9d)
단계 5 : 3-component 손실 정상 작동 → 마스킹 97.5%대 정체
단계 6 : [돌파구] 레이블링 기준 문서화 + 데이터 재레이블 (v9n) → 마스킹 98.75%
         → v9m(97.55%) 대비 +1.2%p — 아키텍처가 아닌 데이터 품질의 효과
단계 7 : L3 임계값 후처리 → 목표 잠정 달성 (MacroF1 98.83%)
단계 8 : OOD 개선 실험 (v14~v17) — dedup_v6 + 감염병 합성 500건 추가
         → L4 F1 87~89%대 하락, 목표 미달성
단계 9 : 전략 전환 — dedup_v7 재구성 + 처음부터 전체 재학습 (v19~v21)
         → v21 MacroF1 95.86%, L4 Precision 89.9% (L3↔L4 경계 혼란)
단계 10: 학습률(LR) 스케줄 최적화 (v22) → 목표 전부 달성 ✅
단계 11: KNN OOD + 3단계 파이프라인 구축 → 신종 재난 탐지 시스템 완성

■ 8. 3단계 추론 파이프라인 (+ LLM Fallback 안전망)
-------------------------------------------------------------------------------
입력 재난문자
     │
     ▼
[1단계] KNN OOD 탐지
  KNN cosine 거리 평균(K=20) > class별 threshold (percentile=96)?
     │YES → "OOD 판정" (신종 재난 가능성)
     │NO
     ▼
[2단계] Confidence Threshold (70%) — Temperature Scaling(T=1.5) 적용
  softmax(logits / T) 최댓값 < 0.70?
     │YES → 판단 유보
     │NO
     ▼
[3단계] v22 분류 → L0 / L1 / L2 / L3 / L4 확정

[OOD 판정 또는 판단 유보 시] → LLM fallback 호출 (4단계 순차 시도, 모두 실패 시 v22 단독 예측 사용)
  ① OpenRouter (gpt-oss-120b:free)
  ② Gemini (gemini-2.5-flash)
  ③ Groq (llama-3.3-70b-versatile)
  ④ Cerebras (gpt-oss-120b)

KNN 파라미터: K=20, cosine distance, brute force
인덱스 규모: train+val 임베딩 116,438건 (CLS 토큰)

class별 OOD threshold (KNN거리 평균, percentile=96 기준):
  L0: 0.018056
  L1: 0.015686
  L2: 0.014583
  L3: 0.007599

■ 8-1. 전체 파이프라인 성능 (test set 20,549건 / T=1.5, conf_thr=70%)
-------------------------------------------------------------------------------
구분                          건수          Accuracy
v22 직접 분류 (모델만으로 확정) 20,103건      99.82%
LLM fallback 호출 대상           446건       41.93%  (호출 실패 0건)
전체 파이프라인                20,549건      98.56%   (MacroF1 97.47%)

[참고] v22 단독 (T=1.5, LLM 없이 모델 예측만 사용): Accuracy 99.26% / MacroF1 98.73%

해석 — 왜 "전체 파이프라인(98.56%)"이 "v22 단독(99.26%)"보다 낮게 나오는가?
  - 이 test set은 분포 내(in-distribution) 데이터라서, 이미 잘 학습된 영역에서는
    모델 단독 예측이 가장 정확함
  - LLM은 모델 스스로 "애매하다"고 판단해 넘긴 446건(전체의 2.2%)만 담당하는데,
    이 구간 자체가 원래 어려운 경계 케이스라 LLM 정확도(41.93%)가 낮게 나오는 것은 자연스러움
  - 즉 평소(분포 내)에는 손해를 약간 감수하고, 안전망의 진짜 가치는 "분포 밖(OOD) 신종
    재난 시나리오"에서 발휘되는 구조 — 그 효과는 9번 OOD 실험에서 직접 확인 가능


■ 9. OOD 실험 결과 (20케이스 신종 재난 시나리오 테스트)
-------------------------------------------------------------------------------
기준: KNN cosine 거리 평균(K=20) vs class별 threshold(percentile=96)
      — 현재 배포 파이프라인(evaluate_pipeline.py / app.py)과 동일한 방식

대상 20개 메시지 중 7개는 학습된 5개 재난유형 범주를 명백히 벗어나는
"노벨(novel) 시나리오" — 해킹/광케이블 절단/태양폭풍/반도체 냉각수/해수면 급상승/
강 댐 균열/핵발전소 냉각계통

결과:
  [OOD 판정]            20개 중 11개 (55%)
  [노벨 시나리오 탐지]    7개 중 3개 (43%)
        → 해수면 급상승, 강 상류 댐 균열, 핵발전소 냉각 계통 이상 등을 정상 탐지

해석:
  - OOD 탐지는 "완벽한 신종 탐지기"가 아니라 "1차 안전망" 역할
  - 미탐지된 노벨 케이스(해킹 전력망 마비, 태양폭풍 GPS 오작동, 반도체 냉각수 유출 등)는
    표현 형식이 기존 학습 분포와 가까워 임베딩 거리상 구분이 어려웠던 경우
  - 탐지에 성공한 케이스는 모델이 "확신을 갖고 틀리는" 대신 LLM fallback으로
    한 번 더 판단할 기회를 거치게 되어, 무대응보다 안전한 결과로 이어짐

[참고] 검증된 향후 개선 방향 — Mahalanobis 거리 기반 OOD score (현재 미반영, 차기 적용 권장)
  raw KNN 평균거리 대신
    score = √((x − μ_c)ᵀ Σ⁻¹ (x − μ_c))   (μ_c = 클래스 평균 임베딩, Σ = 전클래스 공분산)
  로 전환 시:
    → 정분류인데 억울하게 OOD로 거부되는 케이스 134건(−4.7%) 감소
    → 노벨 시나리오 탐지력(3/7)은 그대로 유지
    → "트레이드오프 없는 순개선"으로 9단계 통합 검증까지 완료된 카드
       (자세한 내용: pipeline_v22/OOD_억울한거부_개선_실험_정리.md)


■ 10. 핵심 인사이트 및 결론
-------------------------------------------------------------------------------
1) 레이블 품질이 가장 중요 (단계 6 교훈)
   - 코드/아키텍처 개선 7번 → 마스킹 F1 97.5% 정체
   - 레이블링 기준 문서화 + 재레이블 1번 → +1.2%p 급등
   - "쓰레기 넣으면 쓰레기 나온다 (Garbage In, Garbage Out)"

2) 데이터 편향 제거가 성능과 일반화 모두에 기여 (단계 9 교훈)
   - COVID L0 70% 제거 → COVID 암기 편향 완화
   - dedup_v7 균형 데이터로 처음부터 재학습 → 더 견고한 모델

3) 학습률(LR) 스케줄 최적화로 경계 케이스 성능을 개선 (단계 10 교훈)
   - LR 최적화(lr 5e-5, warmup 20%, epochs 7): L3↔L4 Precision 89.9% → 96.9%
   - 손실 함수 구조를 바꾸지 않고도 학습 스케줄 조정만으로 경계 혼란을 완화할 수 있음을 확인

4) KNN OOD는 신종 재난 탐지의 실용적 해법
   - 20케이스 중 11건(55%) OOD 판정, 노벨 시나리오 7개 중 3개(43%) 탐지
     — 재학습 없이 배포 후 안전망 역할
   - 완벽하지 않지만 Confidence Threshold(70%, T=1.5) + 4단계 LLM fallback과 결합해
     "모델이 스스로 애매함을 인지하고 위임하는" 안전 파이프라인 구성
   - Mahalanobis 거리 기반 OOD score는 노벨 탐지력 유지 + 억울한 거부 134건 감소를
     검증 완료(향후 적용 권장) — 운영 중인 시스템도 계속 개선 여지가 있음을 실험으로 증명

5) 최종 모델 / 파이프라인 사양
   - 모델: model_v22 (KoELECTRA v3 기반), 토크나이저: tokenizer_v22 (vocab 35,000)
   - v22 단독: Accuracy 99.27%, MacroF1 98.75%, L4 Precision 96.9%
   - 운영 파이프라인: pipeline_v22/evaluate_pipeline.py (오프라인 평가) /
     중요파일/hf_space/app.py (FastAPI 데모 서버, 배포용)
   - 전체 파이프라인(LLM fallback 포함): Accuracy 98.56%, MacroF1 97.47%

     - L1 예시: "오늘 밤부터 기온이 영하 20도까지 떨어질 예정입니다. 수도관 동파에 주의하세요."
     - L2 예시: "○○지역 가스관 노후로 인한 누출이 감지되었습니다. 화기 사용을 자제하세요."
     - L3 예시: "○○지역 대규모 산불이 확산 중입니다. 인근 주민은 외출을 자제해 주세요."
     - L4 예시: "○○지역 댐 붕괴 위험으로 즉시 고지대로 대피하시기 바랍니다."
     → 포인트: probs 분포가 정답 라벨에 뾰족하게 몰려 있고, confidence가 높아 "stage":"model"
       로 즉시 끝나는 일반적인 흐름을 보여줌

  ② OOD(신종 시나리오) 케이스 — 안전망이 작동하는 모습 시연
     - 예시: "강 상류 댐 균열이 발견되어 하류 주민들의 고지대 이동을 권고합니다."
       (학습 데이터에 없는 표현 → "ood": true 로 판정 → LLM fallback 호출 → "stage": "llm")
     - 예시: "해수면이 급상승하여 해안 저지대 침수가 진행 중입니다. 고지대로 이동 바랍니다."
     → 포인트: "이 메시지는 모델이 처음 보는 형태의 재난이라고 스스로 판단해서, 한 번 더
       LLM에게 검토를 맡기는 모습입니다" — OOD 탐지 + fallback이 실시간으로 작동하는 것을 시연

  ③ (선택) 저확신(애매한) 케이스 — "ood": false 인데 "stage": "llm" 인 경우
     - 두 라벨 사이 경계에 걸친 표현의 메시지를 사용하면 confidence < 0.70 으로
       판단 유보 → LLM fallback이 호출되는 모습을 보여줄 수 있음
     → 포인트: OOD가 아니어도 "확신이 낮으면" 모델이 스스로 LLM에게 검토를 요청한다는 점

[예상 질의응답 포인트]
  Q. 왜 LLM을 항상 쓰지 않고 모델을 우선 쓰나요?
  A. v22가 직접 처리하는 20,103건은 정확도 99.82%로 LLM(41.93%)보다 훨씬 정확하고 빠름.
     LLM은 모델이 "스스로 애매하다고 판단한" 2.2%(446건)만 담당하는 보조 안전망.

  Q. OOD 탐지가 모든 신종 재난을 잡아내나요?
  A. 아니오. 20개 노벨 시나리오 테스트에서 7개 중 3개(43%) 탐지 — 완벽한 탐지기가 아닌
     "1차 안전망"입니다. 다만 향후 Mahalanobis 거리 기반 score로 전환하면 노벨 탐지력은
     유지하면서 억울한 거부를 134건 줄일 수 있음을 실험으로 검증해 두었습니다.

  Q. LLM 호출이 실패하면 어떻게 되나요?
  A. 4단계(OpenRouter→Gemini→Groq→Cerebras)를 순차 시도하고, 모두 실패하면 v22의
     원래 예측을 그대로 사용합니다 (응답의 "uncertain": true 로 표시).
